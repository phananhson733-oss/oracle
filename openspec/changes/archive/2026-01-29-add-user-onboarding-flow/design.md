## 技术决策

### 决策 1：农历转换实现位置

**选项**：
- A) 前端实现：引入农历转换 npm 包到小程序
- B) 后端实现：后端提供 API，前端调用

**选择**：B) 后端实现

**理由**：
1. 减少小程序包体积（农历库约 30-50KB）
2. 集中管理日期转换逻辑，便于维护
3. 前端不需要处理复杂的闰月逻辑
4. 后端可以做更完善的日期验证

### 决策 2：农历转换库选择

**选项**：
- A) `lunar-javascript`：功能全面，维护活跃，支持 1900-2100 年
- B) `chinese-lunar-calendar`：轻量但功能有限
- C) 自实现：完全控制但工作量大

**选择**：A) `lunar-javascript`

**理由**：
1. 覆盖年份范围足够（1900-2100）
2. 包含完整的闰月处理
3. TypeScript 支持良好
4. 社区维护活跃

### 决策 3：步骤数量设计

**选项**：
- A) 单页表单：所有字段在一页
- B) 两步引导：日期时间 + 地点
- C) 三步引导：日期 + 时间 + 地点

**选择**：B) 两步引导

**理由**：
1. 平衡信息收集完整性和用户体验
2. 日期和时间逻辑相关，放在一起减少认知负担
3. 地点搜索需要独立交互空间
4. 步骤指示器清晰（1/2），用户心理预期明确

### 决策 4：不确定出生时间的处理

**选项**：
- A) 强制填写，不允许跳过
- B) 提供「不确定」选项，默认 12:00
- C) 提供时间精度选择（精确/约/不知道）

**选择**：B) 提供「不确定」选项，默认 12:00

**理由**：
1. 占星学传统：出生时间未知时使用正午 12:00
2. 简化用户决策，只需一个勾选框
3. 通过 `accuracyLevel` 字段记录精度，后续报告可据此调整措辞
4. 避免因强制填写导致用户放弃

### 决策 5：城市数据来源

**选项**：
- A) 使用已有的 `cities.js` 本地数据
- B) 调用后端 API 实时搜索
- C) 调用第三方地理编码 API

**选择**：A) 使用已有的 `cities.js` 本地数据

**理由**：
1. 已有数据覆盖中国所有地级市，满足 90%+ 用户需求
2. 本地搜索响应快，无网络延迟
3. 已实现多种搜索方式（汉字、拼音、拼音首字母）
4. 包含经纬度数据，无需额外查询

## 数据流设计

### 用户资料存储结构

```javascript
// storage key: 'user_profile'
{
  // 基础信息（已有）
  name: string,
  points: number,
  reportCount: number,
  matchCount: number,
  isVip: boolean,
  vipExpireDate: string,

  // 出生信息（新增）
  birthDate: string,           // 公历日期 'YYYY-MM-DD'
  birthTime: string,           // 时间 'HH:mm'
  birthCity: string,           // 城市显示名 '北京, 北京, 中国'
  timezone: string,            // 时区 '8'
  lat: number,                 // 纬度 39.9042
  lon: number,                 // 经度 116.4074
  accuracyLevel: string,       // 'exact' | 'approximate'
  calendarType: string,        // 'solar' | 'lunar'（用户原始选择）
  onboardingCompleted: boolean // 是否完成引导
}
```

### API 接口设计

```typescript
// POST /api/calendar/lunar-to-solar
interface LunarToSolarRequest {
  year: number;       // 农历年，如 1990
  month: number;      // 农历月，1-12
  day: number;        // 农历日，1-30
  isLeapMonth?: boolean;  // 是否闰月，默认 false
}

interface LunarToSolarResponse {
  success: boolean;
  solarDate?: string; // 'YYYY-MM-DD'
  error?: string;     // 错误信息
}
```

## UI 设计规范

### 视觉风格要求

**重要**：引导页面必须与应用整体「水墨古风」视觉风格保持一致。

- **禁止使用 emoji 和彩色图标**：所有视觉元素采用水墨风格
- **色彩克制**：以墨色、宣纸色为主，避免高饱和度色彩
- **留白充足**：遵循中国画「计白当黑」的审美原则
- **字体统一**：标题使用 AncientFont（芝麻行）,正文使用 SourceHanSerifSC（思源宋体）
- **装饰元素**：可适当使用水墨笔触、云纹等传统纹样作为点缀

## 边界情况处理

### 农历转换

| 场景 | 处理方式 |
|------|----------|
| 闰月 | 提供「闰月」勾选框，仅在对应年份有闰月时显示 |
| 日期超出范围 | 提示「请输入 1900-2100 年间的日期」|
| 无效农历日期 | 提示「该日期不存在，请检查」|
| 网络失败 | 显示重试按钮，允许切换回阳历输入 |

### 城市搜索

| 场景 | 处理方式 |
|------|----------|
| 无匹配结果 | 允许用户继续输入，提示「未找到匹配城市」|
| 同名城市 | 显示省份信息区分，如「朝阳, 辽宁」vs「朝阳, 北京」|
| 用户手动输入 | 保存用户输入，但提示「建议选择列表中的城市以确保计算精度」|
| 国际城市 | 支持英文搜索，如「Tokyo」「New York」|

### 表单验证

| 字段 | 验证规则 | 错误提示 |
|------|----------|----------|
| 出生日期 | 必填，不能是未来日期 | 「请选择出生日期」|
| 出生时间 | 勾选「不确定」时可空 | 「请选择出生时间或勾选「不确定」」|
| 出生城市 | 必填 | 「请输入出生城市」|

## 性能优化

1. **城市搜索防抖**：输入 300ms 后才触发搜索，减少计算频率
2. **农历转换缓存**：同一日期的转换结果缓存到内存
3. **表单状态持久化**：步骤切换时保存表单状态，防止误操作丢失
4. **按需加载城市数据**：首次搜索时才加载 `cities.js`

## 可访问性

1. 表单字段添加 `aria-label`
2. 错误提示使用 `role="alert"`
3. 按钮禁用状态有明确视觉反馈
4. 颜色对比度符合 WCAG AA 标准
