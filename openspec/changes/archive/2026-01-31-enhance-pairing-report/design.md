# 架构设计：enhance-pairing-report

## 决策 1：报告展示方式

### 选项
| 方案 | 描述 | 优劣 |
|------|------|------|
| A. 独立页面 | 跳转到新的 pairing-report 页面 | 简洁但多一个页面文件 |
| **B. Step 模式（选中）** | 在 pairing 页面内 step=1/2 切换 | 与 synastry 一致，状态管理简单 |
| C. 弹窗优化 | 保留弹窗但扩大为全屏 | 改动最小但不符合需求 |

**决策**：采用 B 方案。与 synastry 页面保持一致的交互模式，用户心智模型统一。

## 决策 2：内容生成策略

### 选项
| 方案 | 描述 | 优劣 |
|------|------|------|
| A. 纯前端模板 | 扩充前端硬编码文本 | 无 API 依赖但内容同质化 |
| **B. 后端 AI + 缓存（选中）** | AI 生成 + 按组合缓存 | 内容丰富个性化，缓存控制成本 |
| C. 纯实时 AI | 每次实时生成 | 内容最新但成本高、延迟大 |

**决策**：采用 B 方案。配对组合有限（20736 种），缓存命中率高，兼顾内容质量和响应速度。

### 缓存设计
```
缓存 Key：`pairing:${signA}:${signB}:${animalA}:${animalB}`
策略：内存缓存，TTL 24 小时
注意：A-B 与 B-A 视为不同组合（视角不同）
```

## 决策 4：加载体验

采用「快速预览 + AI 增强」的双阶段策略：
1. 点击测算后立即切换到 Step 2，用前端规则快速计算分数并展示
2. 同时请求后端 AI 接口
3. AI 结果返回后平滑替换内容（分数保持前端计算值不变，增加文字解读）
4. 若 AI 超时/失败，前端预计算结果作为兜底

这样用户不会感到明显等待，同时能获得 AI 深度内容。

## 决策 5：提问跳转的上下文传递

通过 URL query 参数传递配对上下文到 ask 页面：
- 轻量级，无需全局状态管理
- 数据量小（星座ID + 生肖 + 摘要）
- ask 页面已有 `onLoad(options)` 参数解析机制

不使用全局 store 或 eventBus，保持最小依赖。
