# Design: 首页优化与个性化推荐系统

## Context

AstroMind 首页是用户进入应用的第一触点，需要在有限空间内完成：
1. 展示今日运势核心信息
2. 引导用户发现和使用核心功能
3. 根据用户状态提供个性化内容
4. 提升用户留存和活跃度

当前首页为静态布局，推荐内容硬编码，无法适应不同用户阶段的需求。

## Goals / Non-Goals

### Goals
- 实现基于用户状态的动态推荐系统
- 提供清晰的功能入口层级
- 支持新用户引导流程
- 支持重要星象事件提醒

### Non-Goals
- 本次不实现数据埋点（后续单独提案）
- 本次不实现推荐算法的 A/B 测试
- 本次不实现推荐内容的后台管理

## Decisions

### 1. 首页布局结构

```
┌─────────────────────────────┐
│  Header (问候语 + 日期 + 头像) │
├─────────────────────────────┤
│  TODAY'S FORTUNE            │
│  (运势卡片 - 保持现有设计)     │
├─────────────────────────────┤
│  快速体验 (3列)              │
│  [双人合盘] [CBT日记] [AI问答] │
├─────────────────────────────┤
│  我的星盘                    │
│  [本命盘解读 →]              │
│  [人生k线图 →]               │
├─────────────────────────────┤
│  为你推荐 (动态 3-4 张卡片)   │
│  [根据用户状态动态生成]       │
└─────────────────────────────┘
```

**决策理由**：
- 运势卡片保持首屏核心位置，符合用户预期
- 快速体验区域提供高频功能快捷入口
- 我的星盘模块聚合个人星盘相关功能
- 推荐模块放在底部，可滚动查看更多

### 2. 推荐优先级算法

采用优先级评分机制，每种推荐类型有固定优先级：

| 优先级 | 类型 | 触发条件 |
|--------|------|----------|
| 10 | 新用户引导 | 注册 ≤3 天 |
| 10 | 本命盘引导 | 未生成本命盘 |
| 9 | 星象提醒 | 有重要星象事件 |
| 8 | 行为推荐 | 基于最近操作 |
| 7 | CBT提醒 | 上次记录 >3 天 |
| 6 | 社交推荐 | 未使用双人合盘 |
| 5 | 热门内容 | 始终展示 |
| 4 | 教育内容 | 始终展示 |

**决策理由**：
- 新用户和核心功能引导优先级最高
- 时效性内容（星象）次之
- 常规内容作为填充

### 3. 后端 API 设计

#### 3.1 用户状态接口

```
GET /api/user/status
Response:
{
  "isNewUser": boolean,        // 注册 ≤3 天
  "registeredAt": string,      // 注册时间
  "hasBirthChart": boolean,    // 是否已生成本命盘
  "hasUsedSynastry": boolean,  // 是否使用过双人合盘
  "lastCBTEntry": string|null, // 上次 CBT 记录时间
  "recentActions": string[]    // 最近操作列表
}
```

#### 3.2 星象事件接口

```
GET /api/astro/events?date=YYYY-MM-DD
Response:
{
  "events": [
    {
      "id": string,
      "type": "mercury_retrograde" | "new_moon" | "full_moon" | "planet_ingress",
      "title": string,
      "description": string,
      "startDate": string,
      "endDate": string,
      "importance": "high" | "medium" | "low"
    }
  ]
}
```

**缓存策略**：
- 前端缓存星象事件数据，有效期 24 小时
- 使用 localStorage 存储，key: `astro_events_cache`
- 每日首次打开时刷新缓存

### 4. 前端数据流

```
onLoad()
  ├─ loadUserProfile()      // 本地存储
  ├─ fetchUserStatus()      // 新增：后端 API
  ├─ fetchAstroEvents()     // 新增：后端 API（带缓存）
  ├─ fetchDailyForecast()   // 现有
  └─ generateRecommendations() // 新增：本地计算
```

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| 后端 API 不可用 | 降级为静态推荐内容 |
| 推荐算法复杂度 | 采用简单优先级排序，避免过度工程 |
| 首页加载性能 | 并行请求 + 骨架屏 + 缓存 |

## Migration Plan

1. 后端先部署新 API（向后兼容）
2. 前端分阶段上线：
   - Phase 1: 布局重构 + 静态推荐
   - Phase 2: 接入用户状态 API
   - Phase 3: 接入星象事件 API
3. 无需数据迁移
