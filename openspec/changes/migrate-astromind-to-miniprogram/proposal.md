# 提案：将 Astromind 迁移为微信原生小程序

**变更 ID**: `migrate-astromind-to-miniprogram`
**提案日期**: 2026-01-22
**状态**: 待审批

---

## 1. 背景与动机

### 1.1 当前状态

**Astromind 项目现状**：
- **技术栈**: React 19 + TypeScript + Vite
- **AI 服务**: Google Gemini API（文本生成 + 图像生成）
- **数据存储**: 前端 localStorage，无后端服务
- **数据来源**: 大量 mock 数据和硬编码内容
- **部署方式**: AI Studio 静态托管
- **代码规模**: ~4350 行 TypeScript/TSX，16 个视图组件

**Oracle_CN 项目现状**：
- **技术栈**: Node.js + Express + TypeScript + PostgreSQL (Supabase)
- **AI 服务**: DeepSeek API（温度分层策略，5 档）
- **核心能力**:
  - Swiss Ephemeris 星历计算（NASA JPL DE431 精度）
  - 完整的用户认证系统（Google/Apple/Email + JWT）
  - Stripe 订阅和支付系统
  - Redis 缓存层（带内存降级）
  - 17 个 API 路由模块
  - 完善的 Prompt 管理系统（版本化）
- **数据库**: PostgreSQL（用户、订阅、购买、合盘记录等 7 张表）
- **部署**: 生产环境服务器

### 1.2 问题陈述

1. **数据真实性缺失**: Astromind 依赖 mock 数据，无法提供真实的占星计算和个性化内容
2. **AI 服务单一**: 仅使用 Gemini API，缺乏 Oracle_CN 的 DeepSeek 深度集成和温度策略
3. **无用户系统**: 无法保存用户数据、订阅状态、历史记录
4. **平台限制**: 当前为 Web 应用，无法利用微信生态的流量和支付能力
5. **架构不一致**: 两个项目技术栈完全不同，无法共享代码和数据

### 1.3 目标

将 Astromind 改造为**微信原生小程序**，并集成 Oracle_CN 的完整后端能力：

1. **前端重构**: 将 React 代码重写为微信小程序原生语法（WXML/WXSS/JS）
2. **后端迁移**: 将 Oracle_CN 后端代码复制到 `astromind/backend/`，独立部署
3. **AI 服务替换**: 移除 Gemini API，完全使用 DeepSeek API
4. **用户系统集成**: 实现微信授权登录 + 独立 Supabase 数据库
5. **数据真实化**: 移除所有 mock 数据，接入真实的星历计算和 AI 生成
6. **代码清理**: 移除 Gemini 相关代码、mock 数据、冗余文件

## 2. 范围

### 2.1 包含的能力

本次变更将实现以下能力增量：

1. **`miniprogram-frontend`**: 微信小程序前端开发
   - 将 React 视图组件重写为小程序页面（5 个 tabBar 主页面 + 9 个功能子页面 + 2 个详情页面）
   - 实现微信小程序导航和生命周期
   - 适配微信 UI 组件和交互规范
   - 集成微信授权登录
   - **页面结构**：
     - TabBar 主页面：首页、探索、运势、发现、我的
     - "发现"的二级入口：AI 顾问、CBT 日记、合盘、实验室、百科、星盘、K 线、配对（9 个）
     - "我的"的功能入口：报告收藏、合盘记录（入口在"我的"，独立页面展示）

2. **`backend-migration`**: 后端服务迁移
   - 复制 Oracle_CN 后端代码到 `astromind/backend/`
   - 配置独立的 Supabase 数据库
   - 迁移数据库 schema（7 张表 + 3 个迁移文件）
   - 配置环境变量和部署脚本

3. **`ai-service-replacement`**: AI 服务替换
   - 移除 `geminiService.ts` 和 Gemini API 依赖
   - 集成 DeepSeek API 服务（复用 Oracle_CN 的 `ai.ts`）
   - 迁移 Prompt 管理系统（版本化 + 缓存）
   - 适配温度分层策略（T1-T5）

4. **`wechat-auth-integration`**: 微信授权集成
   - 实现微信登录流程（wx.login + code2Session）
   - 创建 `users` 表的微信字段（openid, unionid, session_key）
   - 实现 JWT token 生成和刷新
   - 适配 Oracle_CN 的认证中间件

5. **`data-cleanup`**: 数据和代码清理（仅 astromind 项目）
   - 移除所有 mock 数据（~200 行）
   - 移除 Gemini API 相关代码和配置
   - 移除未使用的组件和文件
   - 清理硬编码的用户档案和配置
   - **注意**：Oracle_CN 项目的内容暂不清理，等 astromind 完全完成后再处理

### 2.2 不包含的内容

1. **支付系统**: 暂不集成微信支付（保留 Stripe 后端逻辑，但小程序端不实现）
2. **图像生成**: 移除 Gemini 图像生成功能（DeepSeek 不支持图像生成）
3. **多端适配**: 仅支持微信小程序，不考虑支付宝/抖音等其他平台
4. **数据迁移**: 不迁移 Oracle_CN 的现有用户数据（独立数据库）
5. **UI 重设计**: 不重设计 UI，完全保持 Astromind 的原有 UI 风格和交互逻辑
6. **Oracle_CN 清理**: 暂不清理 Oracle_CN 项目的任何内容，等 astromind 完全完成后再评估

## 3. 架构决策

### 3.1 前端架构

**决策**: 使用微信原生小程序框架（WXML/WXSS/JS）

**理由**：
- 用户明确选择"微信原生小程序"
- 原生框架性能最优，无跨端框架的兼容性问题
- 可以充分利用微信小程序的原生能力（授权、支付、分享等）
- 社区成熟，文档完善

**权衡**：
- ❌ 需要完全重写 React 代码（~4350 行）
- ❌ 无法复用现有的 React 组件和 Hooks
- ✅ 性能和体验最优
- ✅ 无跨端框架的维护成本

**替代方案**：
- Taro 框架：可以保留部分 React 代码，但性能略逊于原生
- uni-app 框架：需要改写为 Vue 语法，学习成本高

### 3.2 后端架构

**决策**: 独立部署后端，复制 Oracle_CN 代码到 `astromind/backend/`

**理由**：
- 用户明确选择"独立部署后端"
- Astromind 和 Oracle_CN 可以独立演进，互不影响
- 便于针对小程序场景优化 API（如简化响应格式、减少字段）
- 独立的部署和监控

**权衡**：
- ❌ 代码重复，需要维护两份后端代码
- ❌ 后续 Oracle_CN 的更新需要手动同步到 Astromind
- ✅ 独立演进，互不影响
- ✅ 可以针对小程序优化

**替代方案**：
- 复用 Oracle_CN 后端：Astromind 直接调用 Oracle_CN 的 API，无需独立部署
  - 优点：代码统一，更新同步
  - 缺点：耦合度高，无法独立优化

### 3.3 数据库架构

**决策**: 创建独立的 Supabase 项目，不共享 Oracle_CN 的数据库

**理由**：
- 用户明确选择"独立 Supabase"
- 数据隔离，避免两个项目的数据互相影响
- 可以针对小程序场景优化 schema（如添加微信特有字段）
- 独立的数据备份和恢复策略

**权衡**：
- ❌ 无法共享用户数据（用户需要在两个平台分别注册）
- ❌ 增加数据库成本
- ✅ 数据隔离，安全性更高
- ✅ 可以独立优化 schema

**Schema 设计**：
- 复用 Oracle_CN 的 7 张表结构
- 在 `users` 表添加微信字段：`wechat_openid`, `wechat_unionid`, `wechat_session_key`
- 保留 `subscriptions`, `purchases`, `free_usage`, `synastry_records`, `subscription_usage` 表
- 暂不实现支付功能，但保留表结构以便后续扩展

### 3.4 AI 服务架构

**决策**: 完全移除 Gemini API，使用 DeepSeek API

**理由**：
- 用户明确选择"完全替换为 DeepSeek"
- Oracle_CN 已有成熟的 DeepSeek 集成（温度分层、缓存、错误处理）
- DeepSeek 成本更低，适合高频调用场景
- 统一 AI 服务，便于维护

**权衡**：
- ❌ 失去 Gemini 的图像生成能力
- ❌ 需要重写所有 AI 调用逻辑
- ✅ 成本更低
- ✅ 复用 Oracle_CN 的 Prompt 管理系统

**图像生成替代方案**：
- 移除所有图像生成功能（`generateCosmicImage`）
- 或使用第三方图像生成 API（如 Stable Diffusion、Midjourney）

### 3.5 认证架构

**决策**: 使用微信授权登录 + JWT token

**理由**：
- 微信小程序的标准认证方式
- 用户体验好，无需输入账号密码
- 可以获取用户的微信头像和昵称

**流程**：
```
1. 小程序调用 wx.login() 获取 code
2. 小程序将 code 发送到后端 /api/auth/wechat
3. 后端调用微信 code2Session API 获取 openid 和 session_key
4. 后端查询或创建用户记录
5. 后端生成 JWT access_token 和 refresh_token
6. 小程序存储 token，后续请求携带 token
```

**权衡**：
- ❌ 仅支持微信登录，无法在其他平台使用
- ✅ 用户体验最佳
- ✅ 符合微信生态规范

## 4. 实施计划

### 4.1 阶段划分

**阶段 1: 后端迁移和配置**（优先级：高）
- 复制 Oracle_CN 后端代码到 `astromind/backend/`
- 创建独立的 Supabase 项目
- 运行数据库迁移脚本
- 配置环境变量（DeepSeek API Key、Supabase 连接、JWT Secret）
- 实现微信授权登录 API（`/api/auth/wechat`）
- 本地测试后端服务

**阶段 2: 小程序前端开发**（优先级：高）
- 创建微信小程序项目结构
- 重写 16 个视图组件为小程序页面
- 实现导航和生命周期管理
- 集成微信授权登录
- 对接后端 API（17 个端点）
- 实现数据缓存和状态管理

**阶段 3: AI 服务替换**（优先级：中）
- 移除 `geminiService.ts` 和 Gemini 依赖
- 集成 DeepSeek API 服务
- 迁移 Prompt 管理系统
- 适配温度分层策略
- 测试所有 AI 生成功能

**阶段 4: 数据和代码清理**（优先级：低）
- 移除所有 mock 数据
- 移除 Gemini 相关代码和配置
- 移除未使用的组件和文件
- 清理硬编码的用户档案
- 代码审查和优化

**阶段 5: 测试和部署**（优先级：高）
- 功能测试（16 个页面 + 17 个 API）
- 性能测试（加载速度、API 响应时间）
- 微信小程序审核和发布
- 后端服务器部署
- 监控和日志配置

### 4.2 依赖关系

```
阶段 1（后端迁移） → 阶段 2（小程序开发）
阶段 1（后端迁移） → 阶段 3（AI 服务替换）
阶段 2（小程序开发） → 阶段 4（代码清理）
阶段 3（AI 服务替换） → 阶段 4（代码清理）
阶段 4（代码清理） → 阶段 5（测试和部署）
```

## 5. 风险评估

### 5.1 技术风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| React 到小程序的重写工作量超预期 | 高 | 中 | 优先重写核心页面，非核心功能可以延后 |
| 微信小程序的 API 限制（如请求并发数、包大小） | 中 | 高 | 使用分包加载、优化图片资源、合并请求 |
| DeepSeek API 的响应速度和稳定性 | 中 | 中 | 实现请求超时和重试机制、使用 Redis 缓存 |
| 独立 Supabase 的成本超预期 | 低 | 低 | 监控数据库使用量，优化查询性能 |
| 微信小程序审核不通过 | 高 | 中 | 提前了解审核规范，避免敏感内容 |

### 5.2 业务风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 用户不接受小程序的交互方式 | 中 | 低 | 保持原有 UI 风格，渐进式优化 |
| 失去 Gemini 图像生成功能导致用户流失 | 中 | 中 | 评估图像生成的使用频率，考虑替代方案 |
| 两个项目的代码同步成本高 | 中 | 高 | 建立代码同步流程，或考虑后续合并后端 |

### 5.3 资源风险

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|----------|
| 开发时间不足 | 高 | 中 | 优先实现核心功能，非核心功能延后 |
| 缺乏微信小程序开发经验 | 中 | 中 | 学习微信小程序文档，参考优秀案例 |
| 后端部署和运维成本高 | 低 | 低 | 使用云服务（如腾讯云、阿里云）降低成本 |
